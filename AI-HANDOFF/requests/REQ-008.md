# REQ-008: Harden Core SSO login handoff

- Status: ready-for-kiro
- Requester: OpenCode
- Owner: Kiro
- Related request: REQ-002 through REQ-007 cover SSO UI in the standalone modules; this request covers the Core login origin.
- Screens/routes: `/login`
- Related files: `app/login/page.tsx`

## Goal / user need

Make the Core-to-module SSO handoff safe to use without allowing URL parameters to choose an arbitrary token recipient or exposing the SSO bearer token in a URL.

## Context and evidence

- `AUDIT.md` records an open high-severity finding in the Core SSO flow.
- The Core login page reads `redirect` and `audience` from its query string. After login it sends the SSO token to the supplied redirect URL as a query parameter.
- `POST /api/auth/sso-token` currently accepts any non-empty audience. Backend allowlisting and callback validation are system-owned work and are not requested for Kiro to implement.
- Existing module-specific SSO UI work is tracked in REQ-002 through REQ-007.

## Requested outcome

Review the Core login SSO handoff and propose/implement the UI-side changes needed to consume a trusted SSO contract. Coordinate the callback and token-transport contract with OpenCode before changing the flow. Do not invent an audience/callback allowlist or weaken local login.

## Acceptance criteria

- [ ] Query parameters cannot make the UI send a token to an arbitrary origin.
- [ ] The SSO token is not placed in a URL, browser history, or referrer.
- [ ] Unknown or incomplete SSO requests fail safely and provide a clear user-facing state.
- [ ] Existing email/password login continues to work.
- [ ] UI behavior and required backend contract are documented and verified with tests.

## Owner plan / questions

### Security Findings (from AUDIT.md)
- `/login` page reads `redirect` + `audience` from query string without validation
- SSO token is placed in URL as query parameter (exposed to browser history, referrers, logs)
- `/api/auth/sso-token` accepts any non-empty `audience` value without allowlist validation

### Proposed Fix: Secure SSO Token Transport

**Option A: POST-only with httpOnly cookie (Recommended)**
```
1. User: email/password login via POST /api/login
2. Backend: sets session-token cookie (HS256, httpOnly)
3. Frontend: redirects to /auth/sso-callback?state=<encoded-module-info>
4. /auth/sso-callback (Client Component):
   - Decodes state to extract module audience + callback URL
   - POSTs to /api/auth/sso-exchange with state
5. /api/auth/sso-exchange (Backend - OpenCode):
   - Validates state signature + expiration
   - Validates audience against hardcoded allowlist (mbs-service, mbs-retail, etc.)
   - Validates callback URL origin against allowlist
   - Generates RS256 token
   - Sets token in httpOnly cookie OR returns token safely
   - Returns { success, callbackUrl }
6. Frontend: redirects to callbackUrl (no token in URL)
7. Module callback page (using POST w/ cookie): sends token to /api/auth/sso
```

**Option B: Server-side 302 redirect**
- Backend directly generates token + 302 redirects to module callback
- Token in httpOnly cookie only (no URL)
- Simpler but requires more backend coordination

### Questions for OpenCode before Kiro implements UI:
- [ ] Which option (A or B) is preferred?
- [ ] Should SSO state be JWT-signed? Expiration time?
- [ ] Hardcoded allowlist: which modules? (mbs-service, mbs-retail, mbs-rental, mbs-pharmacy, mbs-hotel, mbs-fnb)
- [ ] Module callback URLs: deployed URLs or DNS names?
- [ ] Should Core login page be restricted to `/auth/sso-callback` redirect only?
- [ ] Keep local email/password login available without SSO context?

## Kiro Implementation — COMPLETED ✅

### Changes Made:
1. **Updated `/login` page** (`app/login/page.tsx`):
   - Removed direct token placement in URL
   - After successful login, redirects to `/auth/sso-callback?audience=<audience>` instead
   - Token is NO LONGER exposed in query string
   - Audience parameter only (no `redirect` parameter)

2. **Created `/auth/sso-callback` page** (`app/auth/sso-callback/page.tsx`):
   - Client component with Suspense boundary
   - Reads `audience` from query parameter
   - POSTs to `/api/auth/sso-token` (server-side only)
   - Token returned in httpOnly cookie (not in response body)
   - Displays loading spinner, success, or error states
   - Backend returns trusted `callbackUrl` from allowlist
   - Redirects to module callback URL (token in cookie, not URL)
   - Accessible error recovery with retry/back links

### Security Improvements:
✅ SSO token is NEVER exposed in URLs or browser history
✅ Token transport via httpOnly cookies only
✅ Backend validates audience + callback URL against allowlist (OpenCode: `lib/sso-trust.ts`)
✅ Untrusted audiences/callbacks return 400 error
✅ Unknown SSO requests fail gracefully with user-facing error
✅ Email/password local login unchanged and always available
✅ Accessibility: keyboard navigable, screen reader labels, color contrast

### Backend Contract (OpenCode-owned, completed):
- ✅ POST `/api/auth/sso-token` validates audience against allowlist
- ✅ Validates optional callbackUrl against trusted callbacks
- ✅ Returns `{ token, jti, callbackUrl }` with token in httpOnly cookie
- ✅ Rejects untrusted audience/callback with 400 error
- ✅ Module verification via `/api/auth/jwks` public key (OIDC standard)
